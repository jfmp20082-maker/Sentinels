Arquitectura de Sentinela

Cuatro procesos, cuatro lenguajes. Qué hace cada uno, por qué esa tecnología y no otra, y cómo se emplea en el código.

  • 4 procesos
  • 4 370 líneas
  • 6 servidores en la demo
  • 5 s por muestra

El camino de un dato

Una muestra sale del servidor vigilado, se evalúa contra las reglas y aparece en la pantalla del operador sin tocar el panel administrativo. Ese reparto es la decisión estructural de la que cuelgan todas las demás.

Por qué cuatro procesos y no uno

El sistema tiene tres cargas con formas incompatibles. Meterlas en un solo runtime obliga a elegir el peor compromiso para dos de las tres.

Las tres cargas de trabajo
CargaFrecuenciaNaturalezaDónde vive
Leer sensores del SO cada 5 s por host acceso al sistema, multiplataforma agent-java/
Evaluar reglas y difundir cientos de eventos/s flujo, muchas conexiones abiertas realtime-node/
Login, catálogo, preferencias decenas de peticiones/min CRUD transaccional api-php/

Separadas, cada una usa la herramienta que le corresponde y escalan por su cuenta: si entran trescientos servidores nuevos se replica el gateway, no el panel.

Java 17 · sin dependencias

El agente en cada servidor

Mide, firma y envía. Nada más.

Por qué

Es el único lenguaje de la pila que corre igual en Linux, Windows y macOS con un solo artefacto compilado, que es exactamente el requisito de una flota mixta. OperatingSystemMXBean entrega CPU, memoria física, swap y carga del sistema con la misma llamada en los tres. La JVM ya trae HTTP y criptografía, así que el agente no baja una sola librería: se instala en máquinas ajenas y cada dependencia sería superficie de ataque y parcheo ajeno.

Cómo se usó

  • Agent.java — bucle de un solo hilo, firma HMAC-SHA256 de cada muestra y cola local de 500 entradas que retiene lo que no se pudo entregar. Un agente que pierde datos durante un corte no sirve para investigar ese corte.
  • Collector.java — lo que la JVM sabe va por JMX; lo que no (temperatura, servicios, logs de autenticación) tiene una rama por sistema: systemctl y /sys/class/thermal, sc query y WMI, launchctl.
  • Json.java — noventa líneas de serializador propio, por la misma razón que no hay dependencias.

El JSON de salida es idéntico en los tres sistemas operativos. Ni el gateway ni el frontend saben nunca en qué SO corre cada agente.

Node 22+ · TypeScript · ws

El gateway de tiempo real

Ingesta, motor de alertas y difusión.

Por qué

Resuelve dos cosas que PHP hace mal. Primero, miles de conexiones abiertas durante horas: el modelo de PHP termina el proceso al responder, el bucle de eventos de Node sostiene los WebSockets con memoria casi plana. Segundo, estado entre muestras: el motor recuerda desde cuándo se cumple una condición, para no gritar por un pico de un segundo, y qué alertas ya avisó. Eso es memoria viva entre peticiones, algo que PHP no tiene sin meter Redis de por medio.

Cómo se usó

  • index.ts — /ingest verifica la firma con timingSafeEqual, no con ===.
  • hub.ts — el upgrade del WebSocket solo se acepta si el token del panel es válido en PHP. Guarda 60 muestras por servidor para que un cliente recién conectado vea la gráfica completa desde el primer frame.
  • alerts.ts — umbrales con histéresis, servicio caído, paso a UPS, puertos fuera de línea base e intentos de acceso fallidos. Las caídas se detectan por silencio, en un temporizador: un servidor apagado justamente deja de enviar datos.
  • simulator.ts — seis agentes falsos que firman con el mismo HMAC. El gateway no los distingue de agentes reales, que es la prueba de que el contrato está bien definido.

TypeScript no es cosmético. El agente escribe un JSON de treinta campos anidados que atraviesa tres procesos. shared/types.ts es la única definición de ese contrato y la comparten gateway y navegador: si se renombra mem_used_mb, el compilador señala los dos lados. En JavaScript plano eso sale en producción como undefined en una gráfica.

Node 22+ ejecuta .ts directamente, así que el gateway no tiene paso de compilación: node src/index.ts y listo. Por eso el tsconfig activa erasableSyntaxOnly y el código evita enum y propiedades de constructor.

PHP 7.3+ · PDO · sin framework

La API del panel

Identidad, 2FA, catálogo y preferencias.

Por qué

Aquí PHP sigue siendo la opción sensata: CRUD transaccional, sesiones y un despliegue que consiste en copiar archivos. Trae de fábrica justo lo que importa — password_hash() con sal automática, hash_equals() para comparar en tiempo constante, hash_hmac() y PDO con sentencias preparadas.

Cómo se usó

  • Sin framework. Quince endpoints no ganan nada cargando Laravel; se pierde legibilidad y tiempo de arranque.
  • Auth.php — login en dos pasos. El primer token nace en estado pending_2fa y no abre ningún dato. Bloqueo a los cinco intentos, y password_verify se ejecuta incluso cuando el usuario no existe, para que el tiempo de respuesta no revele qué identificadores son válidos.
  • Totp.php — RFC 6238 a mano, ciento diez líneas, sin Composer. Compatible con Google Authenticator, Authy y las claves de verificación de iOS.
  • Db.php — PDO sobre SQLite. Nada del SQL es propietario: pasar a MySQL o PostgreSQL es cambiar el DSN.

La decisión de las IP. Cuando el usuario oculta una dirección, la API devuelve ip_private: null. No se enmascara en el cliente, porque enmascarar en el cliente es teatro: el dato seguiría en el JSON de la pestaña de red.

React 19 · Bootstrap 5 · SVG

La interfaz

Acceso, tablero de mosaicos e inventario.

React 19, donde gana algo

NovedadDóndeQué resuelve
useActionState Login El formulario es una función async; React gestiona pendiente, error y doble envío. Cero useState de «cargando».
useFormStatus Botón de envío El botón sabe solo si su formulario está enviando, sin recibir props.
useOptimistic Mosaicos, IP El mosaico se mueve y el ojo cambia en el mismo frame; si el guardado falla, React revierte.
use(Context) Sesión Lee el contexto sin useContext y sin las restricciones de los hooks clásicos.
<title> en componente Login, panel React sube los metadatos al <head>; sobra react-helmet.

El problema de rendimiento

Llegan hasta seis muestras por segundo. Si cada una hiciera setState en la raíz, React recorrería el árbol completo doce veces por segundo y la interfaz se arrastraría. La solución está en useStream.ts: un store externo con useSyncExternalStore y suscripciones por clave. Un dato nuevo de srv-db-01 re-renderiza el mosaico de srv-db-01 y nada más.

Bootstrap, sin pelearse con él

El tablero se apoya en la rejilla de doce columnas: cada mosaico declara su ancho y el navegador hace el reflujo, incluido el responsive. Eso ahorra una librería de dashboard grid entera, y viene resuelto lo aburrido y fácil de hacer mal: foco visible, contraste de formularios, tablas responsivas.

La personalización no sobreescribe las clases de Bootstrap: redefine sus variables (--bs-body-bg, --bs-primary, --bs-border-radius) y añade las del proyecto. Actualizar Bootstrap no rompe el tema. De su JavaScript solo se carga el menú desplegable; el panel lateral lo controla React, porque mezclar los dos sistemas de estado termina en paneles que no se cierran.

Las gráficas son SVG escrito a mano: un medidor y una serie temporal son unas cuarenta líneas cada uno. Chart.js sumaría 200 kB y un <canvas> que hay que redibujar en pantallas Retina y en cada cambio de tamaño.

Qué se probó de verdad

El prototipo se ejecutó de punta a punta con seis agentes simulados emitiendo cada dos segundos. Estas cifras salieron de esa corrida, no de una estimación.

401 Respuesta de /api/servers con el token del primer paso, antes de validar el código TOTP.
17 s Desde que se detuvieron los agentes hasta la alerta de falta de latido en los seis servidores.
86 kB JavaScript de producción comprimido, con React 19 y Bootstrap completos dentro.
6 Tipos de alerta disparados en vivo: CPU, memoria, servicio detenido, temperatura, fuerza bruta y apagón con UPS.

Lo que todavía no es

Un prototipo honesto declara sus huecos. Ninguno de estos es difícil; simplemente no está hecho.

  • TLS Todo va en claro. En producción, nginx con certificados y el token de sesión en una cookie HttpOnly; Secure; SameSite=Strict en vez de sessionStorage.
  • Histórico El gateway guarda sesenta muestras en memoria. Para gráficas de días hace falta una base de series temporales alimentada desde el mismo /ingest.
  • Móvil La interfaz es responsiva y el registro de dispositivos ya existe, pero falta el envío real a APNs y FCM.
  • Demo El endpoint /api/demo/totp entrega el segundo factor a quien lo pida. Solo existe si está el archivo api-php/data/DEMO; hay que borrarlo antes de cualquier despliegue.
  • Java El agente está escrito y revisado, pero no se compiló: la máquina de desarrollo no tenía JDK. El simulador cubre su lugar en la demo.
